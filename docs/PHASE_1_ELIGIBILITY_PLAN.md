# Phase 1 — Economic Eligibility Plan

**Status:** implementation sequence for review; no Phase 1 implementation or automation is authorized by this document. **Evidence baseline:** repository `main` at `5ab7b7339f706a16c855446b5e6563179f1b880f`, the [canonical finance register](FINANCIAL_BUGS.md), [finance automation roadmap](FINANCE_AUTOMATION_ROADMAP.md), and [Shopify discoveries](SHOPIFY_DISCOVERIES.md). Production observations below are the already-recorded Audit F and supplied FIN-BUG-009 verification, not new production access. FIN-BUG-009 remains `FIXED_NOT_VERIFIED` and is not reopened here.

## 1. Scope and current flow

Phase 1 concerns whether an existing economic source may enter settlement. It does **not** activate automatic settlement, approve an existing DRAFT, change Shopify refund authority, or repair historical financial records.

| Stage | Current authority and behavior |
| --- | --- |
| Commerce/operations | Allocation-scoped order, fulfillment, return, refund and cancellation records; canonical Shopify refund monetary evidence is admitted through the existing ingestion gate. A later Shopify read is not proof of an earlier refund observation. |
| SALE finance | `FinanceLedgerEntry` preserves commission and settlement-delay snapshots. `VendorAllocation.shippingStatus` must indicate delivered; `resolveSettlementDeliveryDate` currently uses mutable `Fulfillment.shipmentUpdatedAt`. `evaluateSaleSettlementDelay` compares that time plus the SALE's frozen delay with the evaluation time. |
| Preview | `buildApprovalPreview` selects ledger rows, applies `rowIsEligible`, removes rows with blocking `FinanceIntegrityAlert`, removes rows already in active approvals, then builds monetary lines. Selected-order diagnostics are built separately from the original rows and do **not** receive the final alert-filtered set. |
| DRAFT | `createDraftApproval` calls the same preview builder inside a Serializable transaction and freezes its selected lines and snapshots. The DRAFT does not itself prove approval-time eligibility. |
| APPROVED | `validateSettlementApprovalBeforeApprove` reloads each source. SALE lines receive an explicit `evaluateSaleSettlementDelay` check, alongside refund-arrival, return/hold, integrity-alert, amount and other revalidation. Approval remains the current write boundary. |
| UI | Scheduled READY is preview-level, not an approval guarantee. Selected-order diagnostics and settlement queue tabs can present classifications that differ from final backend selection/detail evidence. Current profile delay displayed in schedule UI is not every SALE's frozen delay. |

The existing approved/frozen settlement, SALE/REFUND ledger, refund evidence, payout and Financial Correction authorities remain untouched in every proposed package. Source eligibility can change between preview, DRAFT and approval; appropriate later revalidation is intentional, whereas disagreement for the **same evidence and time** is a defect.

## 3. Blockers, decisions and Shopify boundary

**Decisions required before affected later packages, not before the first package:**

1. FIN-BUG-003: define authoritative delivered-event time, what to do when it was never retained, and whether a prospective-only cutoff can coexist with old DRAFT/APPROVED authority. Do not substitute `fulfilledAt` or a mutable latest event by name alone.
2. FIN-RISK-001, after reachability proof: decide which actual return states and quantities hold which allocation/SALE economics, including simultaneous refunded and unrefunded returns. Audit F overlap is not proof that every open-looking return blocks settlement.
3. Before automatic eligibility or future-dated scheduling: decide whether maturity may be drafted using future/end-of-day `asOfDate`, and whether unresolved terminal refund evidence blocks new automated progression. Existing manual paths and review semantics are not rewritten by this plan.
4. FIN-UI-001's full closure additionally needs Phase 3's cancelled-cycle replacement/identity decision; a READY preview is not durable approval authority.

**Shopify clarification required for the first package: none.** It reads already-persisted local alert and preview evidence and must not call Shopify. FIN-BUG-001 likewise changes only local SALE/REFUND eligibility parity and does not need a new Shopify monetary assumption. If FIN-BUG-003's approved solution relies on Shopify delivery events, ask Shopify AI/official documentation **before that package**:

> For Admin GraphQL API 2026-01, what exact `FulfillmentEvent` status and timestamp establish delivery for a particular fulfillment/line item? Is the event's `happenedAt` and identity immutable across later canonical reads, or can delivery events/times be edited, supplemented, removed or reordered? If a later read cannot prove the first observed delivery time, what immutable event/revision evidence, if any, does Shopify expose? Confirm behavior when no delivery event is returned or only fulfillment `updatedAt` changes.

This is a clarification question, not an assumed answer or approval to backfill historical delivery times. No Shopify clarification can replace the product decision about which evidence Sporgym uses for settlement maturity.

## 4. Dependency-safe sequence

1. **First: FIN-BUG-004 + FIN-TEST-005 diagnostic parity.** No monetary membership/predicate change, product choice, Shopify call, migration or historical rewrite. Verify the final candidate list and diagnostic describe the same selected ledger row.
2. **Separate profile-state package: FIN-BUG-006 + FIN-UI-009.** Preserve inactive records during ordinary Admin read/edit/save, while proving vendor/scheduler consumers retain their intended boundaries. This protects future scheduling without coupling it to SALE delay changes.
3. **SALE eligibility parity: FIN-BUG-001 + FIN-TEST-002.** Specify the already-enforced approval maturity rule across preview/DRAFT for SALEs with refund impact; keep REFUND authority and all other holds. Because future settlement membership changes, require paired real-DB stage tests and read-only production impact assessment before deployment.
4. **Independent presentation work: FIN-UI-003/FIN-TEST-006 and FIN-UI-010.** Queue/detail classification and current-versus-frozen delay labels can follow their respective evidence; neither is a substitute for economic predicate repair.
5. **Delivery-time authority: FIN-BUG-003/FIN-TEST-003.** Wait for the delivery-time/legacy policy and any necessary Shopify event clarification; then specify prospective persistence, history boundary and repeated-refresh regressions. No inferred migration.
6. **Return-hold risk: FIN-RISK-001/FIN-TEST-004.** First prove a valid multi-return configuration, then resolve the policy question if it exists. Do not label it a confirmed bug yet.
7. **Phase 1 integration and Phase 2 shadow gate.** Pair preview, DRAFT and approval on identical and intervening evidence; inspect alert/hold/refund/correction exclusions, source-specific delay, UI explanation and PostgreSQL concurrency. No automatic economic write until the roadmap's approved decisions and shadow acceptance are complete.

This is dependency order, not a ranking of customer impact. Independent UI/profile work may be scheduled separately; it must not be bundled into the first package merely because it is also spec-ready.

## 5. First implementation package — selected, not started

**Package:** FIN-BUG-004 selected-order integrity-alert diagnostic parity, with FIN-TEST-005. **Intended behavior:** for a matched selected ledger row removed from preview by an existing blocking `FinanceIntegrityAlert`, `candidateIncluded=false`, a truthful exclusion reason, and no corresponding monetary line. If the alert resolves, the same otherwise-eligible row may be reported included through the existing preview predicate. Multi-row orders must not acquire a new order-wide inclusion rule; diagnostics must identify the actual selected ledger row/final candidate membership.

| Contract element | Boundary |
| --- | --- |
| Likely code | `backend/src/modules/finance/settlement-approval.service.ts`: `buildApprovalPreview`, `buildSelectedOrderDiagnostics`/`buildMatchedOrderDiagnostic`, using the already-computed integrity-safe/final candidate set or its exact blocker evidence. Existing `findBlockingFinanceIntegrityAlerts` semantics remain authoritative. `src/settlement-approval.test.ts` is the focused test location. Route/UI changes are **not expected** unless the existing DTO cannot express the truthful reason. |

| Deterministic tests | Selected order with one otherwise-eligible SALE and a blocking alert: diagnostic excluded, reason identifies existing alert category, line absent, count/totals unchanged from current safe preview; same row without alert included; active-approval and cross-vendor cases retain prior diagnostics; representative multiple-ledger order does not gain an inferred order-wide rule. Assert preview and DRAFT use the same financial line set. Test API serialization only if the diagnostic DTO changes. |
| Production verification | After a separately approved deployment, read-only preview/GET on a naturally existing selected-order alert case if available; compare diagnostic, line list and total without creating a settlement. | Storage and rollback | Prisma/schema/migration: **not expected**. Production data mutation: **none from this diagnostic fix**. Reverting this package restores the old diagnostic wording but does not reverse any settlement or change historical authority. |

**Required decisions before implementing this first package: none.** Engineering must confirm the exact diagnostic reason/DTO within existing alert semantics and retain per-row (not guessed order-wide) meaning. No business rule, external provider answer, new permission or automatic settlement action is needed.

## 6. Non-goals and Phase 1 exit

No Phase 1 package may rewrite an APPROVED settlement or PAID payout, recalculate historical SALE/refund snapshots using today's vendor profile, infer a delivered event from `fulfilledAt`, treat a later Shopify refund read as historical proof, silently release a return hold, ignore an alert/correction, auto-approve a settlement, or advance any payout/payment state. The plan does not fix Phase 3 cycle identity, define EFT or Logo invoice gates, or change FIN-BUG-009 status.

Phase 1 exits only when the applicable product/Shopify authority questions are answered; accepted source/hold rules are consistent at preview, DRAFT and approval for the same evidence/time; future-delivery and legacy-unknown handling is explicit; targeted unit/UI and real-PostgreSQL boundary/concurrency tests pass; no historical authority is rewritten; and Phase 2 read-only shadow has an approved acceptance contract. A green diagnostic-only package alone does **not** make Phase 1 or automated settlement ready.
