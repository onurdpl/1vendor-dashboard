# FIN-BUG-009 — Legacy Payout Lineage Compatibility Specification

**Phase:** Phase 0 — Legacy / Production Compatibility. **Type:** pre-implementation design only. **Evidence baseline:** repository `main` at `4b9f2885cd38b7dd70c86c6358af41a59c5fb148`; Audit F/G production observations as recorded in [the canonical register](FINANCIAL_BUGS.md). This document authorizes neither code changes nor production data remediation. It does not close FIN-BUG-009 or answer the wider payout grouping questions in FIN-DESIGN-004. It follows [roadmap Phase 0](FINANCE_AUTOMATION_ROADMAP.md).

## Problem and evidence strength

Audit F reported three production `PayoutBatch` records, all DRAFT, with 11 `PayoutBatchLine` rows. Every line has `financeLedgerEntryId` present and `settlementApprovalLineId = NULL`. In that **observed 11-row population**, each ledger ID mapped to exactly one `SettlementApprovalLine` and one `SettlementApproval`; no orphan or ambiguous mapping was found. Two payouts derive from one settlement each, and one derives from two. This is **CODE-BACKED PRODUCTION EXPOSURE**, not an observed failed production REVIEW request: none was attempted.

Current `validatePayoutBatchBeforeTransitionWithClient` reports `settlement_approval_line_missing` for a NULL direct link. `markPayoutBatchReview` invokes that validator; `markPayoutBatchPaid` requires REVIEW, invokes it again, and `buildPayoutPaidEvents` independently requires the direct ID. The focused missing-backing test expects rejection. A repair limited to DRAFT → REVIEW validation would therefore still leave Mark Paid blocked. The problem is lineage compatibility, not an authorization to recompute historical money or initiate EFT.

The direct settlement line is current preferred authority. Derivation through ledger ID is **not** globally deterministic: the schema permits multiple approval lines for one ledger, including historically CANCELLED or inactive approvals. Filtering to an APPROVED candidate before counting could accidentally choose a newer approval that was not the original basis of a NULL-linked payout. Likewise, matching by order number, amount alone, current Shopify state, or arbitrary nearest timestamp would be a guess. None is allowed.

## Non-negotiable compatibility contract

1. Never recalculate payout or settlement amounts, change `amountSnapshot`, rewrite FinanceLedgerEntry or SettlementApproval/Line, or mutate accepted refund/Financial Correction authority. Do not change a PAID payout or automatically progress a DRAFT to REVIEW/PAID.
2. For a non-NULL `settlementApprovalLineId`, use **only** that direct link and existing validation. Do not fall back if it is broken, stale, wrong-vendor, cancelled or mismatched. A direct-link failure is not a legacy missing-link case.
3. For an unpaid ordinary `PayoutBatchLine` with NULL direct link and present ledger ID, obtain **all** `SettlementApprovalLine` rows referencing that ledger, without silently discarding CANCELLED/DRAFT rows before the ambiguity count. Require exactly one total candidate. Then require its parent APPROVED, vendor and currency equal the batch, ledger ID equal the payout line, recognized line type consistent with the ledger/refund-adjustment path, and frozen `payableImpactMinor` exactly equal the payout line's amount snapshot under existing minor-unit conversion. Reuse all existing hold, alert, active-membership, correction-coverage and amount checks. Zero or more than one candidate, absent ledger, scope/type/amount mismatch or inactive settlement fails closed with a structured transition blocker; no auto-selection.
4. Ensure the effective resolved settlement line is unique within this payout and not claimed by a different active payout. A pair of NULL-linked lines must not both borrow the same resolved settlement line. Modern direct lines and historical NULL lines must be considered together for membership/conflict checks; otherwise the nullable FK's relation query can miss legacy claims. This is a validation requirement, not permission to reallocate sources.
5. Resolve from persisted local financial history, not a later Shopify read. Audit F's deterministic 11-row observation supports testing a candidate compatibility route, but fresh read-only prechecks must confirm current status, uniqueness, amounts and blockers before any production transition.
6. New ordinary payout preparation must continue to persist the exact direct settlement-line ID. A NULL on a newly created line is a regression; the compatibility branch must not become a normal writer path. The current schema has no reliable immutable "legacy version" marker, so NULL + proven unique frozen local lineage is a **structural compatibility shape**, not proof of creation date. Do not invent a calendar cutoff. If product insists on historical identity rather than structural eligibility, that requires separate provenance/approval before implementation.

### REVIEW transition

Within the transition transaction, each line uses either its direct ID or a strictly validated unique historical resolution. The resolver should produce an in-memory effective settlement-line view for the complete current validator, including correction coverage that currently traverses `line.settlementApprovalLine`. A successful DRAFT → REVIEW changes only the authorized payout status; it does **not** populate a formerly NULL direct field or alter settlement/ledger authority. A missing/ambiguous/ineligible match returns a blocker and leaves DRAFT unchanged. A successful match is not a waiver for late refunds, return/cancellation holds, voided/paid ledger, amount drift or another active payout.

### Mark Paid transition

Re-resolve and revalidate in the Mark Paid transaction after its existing batch row lock. Do not rely on a REVIEW-time result: source state can change between transitions. The same effective line IDs used by revalidation must be passed to `buildPayoutPaidEvents`, whose current metadata and idempotency key require the settlement-line ID. They remain stable only when the candidate remains uniquely authoritative; newly missing/ambiguous/inactive lineage fails closed before PAID, ledger update or events. The paid event should reference the proven settlement-line ID, while the historical payout row may remain NULL; no synthetic ID or metadata-only authority. Existing PAID rejection, unique FinanceEvent idempotency and transaction rollback remain. Any uncertainty around event/source consistency under concurrent settlement changes needs isolated PostgreSQL proof before release.

### Historical detection and current payout creation

No repository field establishes a trustworthy pre-/post-migration version for each payout line. `createdAt` alone is not approved as a cutoff, and migration date is not proof of row provenance. The narrow structural fallback is NULL direct link + required ledger ID + exactly one total candidate + valid frozen amount/type/scope + current unpaid transition state. It applies only to ordinary payout lines; correction payout/source rows retain their own lineage. This cannot distinguish a future malformed NULL row from a historical NULL row, so protect the **writer** with a direct-link regression and diagnostics for any newly observed NULL. If an immutable, auditable age/provenance restriction is required, that is missing evidence, not a reason to fabricate a cutoff. Current `preparePayoutBatch` already writes the direct link, so FIN-BUG-009 remains a historical compatibility issue rather than a proven broad writer defect.

## Option assessment

| Option | History / audit and authority risk | REVIEW, PAID, cancellation, new payouts | Concurrency, rollback, migration, approval |
| --- | --- | --- | --- |
| **A. Strict runtime compatibility** — direct link first; NULL-only unique all-status ledger resolution, then normal checks. | Non-destructive. Audit F's mapping can be re-proven at runtime; no silent field change. Must pass effective ID through all validator and PAID event/coverage consumers. | Supports both transitions if implemented end-to-end. Cancellation unchanged; modern direct links remain primary. | Re-evaluate on each transition, test competing claims/status changes in real PG. Reverting code restores prior fail-closed behavior, though a payout already manually PAID cannot be undone. No DB migration or production data mutation expected. Design approval and operational transition approval still required. |
| **B. One-time backfill of historical direct IDs.** | Changes historical payout rows and makes inferred lineage look originally persisted; needs explicit before/after audit and could conceal uncertainty. Audit F matches alone do not authorize it. | Existing REVIEW/PAID code may then work, but freshness/holds still apply. New payouts unaffected; cancellation does not require it. | Race with transition/settlement changes; controlled SQL, backup, rollback and production authorization required. Do **not** choose merely for convenience. |
| **C. Separate immutable compatibility/remediation record.** | Retains original NULL and an auditable mapping decision; introduces a new authority that must be consulted consistently. | Can support both transitions only if validator/event/coverage code reads it; cancellation can remain unchanged. Modern direct path unaffected. | New schema/migration, unique identity and concurrency policy, extra operational workflow/rollback. Justified only if audit requirements cannot be met by strict runtime proof. Product/finance approval required. |
| **D. Leave historical DRAFTs blocked and cancel/recreate manually.** | Smallest code delta (none), but cancellation/recreation changes batch identity and potentially frozen payout/debt source set. It is **not** equivalent to preserving the three existing DRAFTs. | No compatibility for REVIEW/PAID; current cancellation remains. New direct-link payouts may prepare from then-current sources only. | No code migration, but material production finance workflow and external EFT uncertainty demand separate decision and authorization; not a safe default. |

**Recommendation: Option A, strict runtime compatibility, as the pre-implementation target.** It is the smallest non-destructive route supported by current code and Audit F's observed unique lineage, provided the resolver supplies a single effective view to **both** transition validation and Mark Paid event creation, and all ambiguity/amount/status/membership checks above pass. Option B mutates historical rows; C adds authority/schema complexity; D discards the goal of retaining usable DRAFTs. This is a design recommendation, **not** implementation approval or a claim that the three production batches are presently transition-eligible. Should isolated PG tests show that existing correction-coverage or membership behavior cannot use a nonpersisted effective line without widening finance semantics, stop and reassess the recommendation before coding around it.

## Production boundary, rollout, rollback and closure

**Code compatibility deployment (A):** A later, separately approved release could add the strict local resolver and tests without a Prisma migration or direct production data mutation. It must remain disabled or fail closed until isolated tests and a fresh read-only production precheck show that the targeted batch/line IDs still have one total lineage candidate each, exact amount/type/vendor/currency/APPROVED status, no conflicting active claim, and no other transition blockers. A successful deployment alone does not move any batch; Admin still explicitly requests REVIEW and later Mark Paid only after the external payment workflow. Existing generic cancellation behavior remains.

**Production data remediation (B/C): NOT AUTHORIZED.** If runtime compatibility proves insufficient, design a separate, auditable procedure with exact targeted records, fresh read-only precheck, approved mutation authority, backup/recovery plan and controlled after-check. Do not write or run backfill SQL now, silently fill the 11 IDs, or alter amounts/history. Do not assume production EFT state from DRAFT.

**Rollback:** Reverting compatibility code returns NULL-linked payouts to their prior blocked state without undoing a completed manual transition. A payout once legitimately marked PAID remains terminal; financial history and external EFT cannot be rolled back by code deployment. Any contemplated DB backfill would need its own separately approved rollback boundary.

**FIN-BUG-009 remains OPEN** until: design approved; historical NULL-line fixture and uniqueness proof; REVIEW and Mark Paid compatibility where applicable; missing/ambiguous/ineligible fail-closed cases; modern direct-link behavior unchanged; relevant correction/PAID regressions; real PostgreSQL/integration and concurrency proof; controlled deployment; post-deploy read-only production verification; and, if needed, separately authorized, controlled production transition verification. An actual production transition result is currently UNKNOWN.

## Proposed single implementation package — not an implementation prompt

**Package name:** FIN-BUG-009 Legacy Payout Lineage Compatibility.

- **Expected files:** narrowly scoped `backend/src/modules/finance/finance.service.ts` for resolver/effective-line use at both transitions and event creation; `src/payout-batch-preparation.test.ts` for focused service behavior; one isolated PostgreSQL payout-transition test file if no existing fixture can cover the required real-DB cases. - **Rollback consideration:** code rollback is possible before a manual transition; do not imply that PAID finance or EFT is reversible. No historical rows are rewritten by this recommended package.
