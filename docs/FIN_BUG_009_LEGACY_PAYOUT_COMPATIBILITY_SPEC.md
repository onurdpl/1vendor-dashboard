# FIN-BUG-009 — Legacy Payout Lineage Compatibility Specification

**Phase:** Phase 0 — Legacy / Production Compatibility. **Type:** approved compatibility specification, amended after an isolated PostgreSQL safety regression. **Evidence baseline:** repository `main` at `4b9f2885cd38b7dd70c86c6358af41a59c5fb148`; Audit F/G production observations as recorded in [the canonical register](FINANCIAL_BUGS.md). The cancellation regression was reproduced against the uncommitted implementation at `beb7aa948cbf0d70a2daeaa353f68b0a85f4eb5d`; this SHA does not replace the original evidence baseline. This document authorizes neither production data remediation nor an actual payout transition. It does not close FIN-BUG-009 or answer the wider payout grouping questions in FIN-DESIGN-004. It follows [roadmap Phase 0](FINANCE_AUTOMATION_ROADMAP.md).

## Problem and evidence strength

Audit F reported three production `PayoutBatch` records, all DRAFT, with 11 `PayoutBatchLine` rows. Every line has `financeLedgerEntryId` present and `settlementApprovalLineId = NULL`. In that **observed 11-row population**, each ledger ID mapped to exactly one `SettlementApprovalLine` and one `SettlementApproval`; no orphan or ambiguous mapping was found. Two payouts derive from one settlement each, and one derives from two. This is **CODE-BACKED PRODUCTION EXPOSURE**, not an observed failed production REVIEW request: none was attempted.

At the original baseline, `validatePayoutBatchBeforeTransitionWithClient` reports `settlement_approval_line_missing` for a NULL direct link. `markPayoutBatchReview` invokes that validator; `markPayoutBatchPaid` requires REVIEW, invokes it again, and `buildPayoutPaidEvents` independently requires the direct ID. The focused missing-backing test expects rejection. A repair limited to DRAFT → REVIEW validation would therefore still leave Mark Paid blocked. The problem is lineage compatibility, not an authorization to recompute historical money or initiate EFT.

An isolated PostgreSQL regression against the current uncommitted runtime resolver proved an additional consequence of the same NULL lineage: a uniquely resolved historical payout can reach REVIEW and PAID while retaining its NULL direct field, after which `cancelSettlementApproval` can still cancel its backing approval. Its paid-payout guard joins `PayoutBatchLine` to `SettlementApprovalLine` only through `settlementApprovalLineId`, so the historical PAID line is invisible. The test expected rejection but the cancellation returned success. This was **not** a production transition or production cancellation. FIN-BUG-009 covers both transition compatibility and this paid-history cancellation protection; FIN-DESIGN-004 remains the distinct grouping/migration question. No new FIN ID is required.

The direct settlement line is current preferred authority. Derivation through ledger ID is **not** globally deterministic: the schema permits multiple approval lines for one ledger, including historically CANCELLED or inactive approvals. Filtering to an APPROVED candidate before counting could accidentally choose a newer approval that was not the original basis of a NULL-linked payout. Likewise, matching by order number, amount alone, current Shopify state, or arbitrary nearest timestamp would be a guess. None is allowed.

## Non-negotiable compatibility contract

1. Never recalculate payout or settlement amounts, change `amountSnapshot`, rewrite FinanceLedgerEntry or SettlementApproval/Line, or mutate accepted refund/Financial Correction authority. Do not change a PAID payout or automatically progress a DRAFT to REVIEW/PAID.
2. For a non-NULL `settlementApprovalLineId`, use **only** that direct link and existing validation. Do not fall back if it is broken, stale, wrong-vendor, cancelled or mismatched. A direct-link failure is not a legacy missing-link case.
3. For an unpaid ordinary `PayoutBatchLine` with NULL direct link and present ledger ID, obtain **all** `SettlementApprovalLine` rows referencing that ledger, without silently discarding CANCELLED/DRAFT rows before the ambiguity count. Require exactly one total candidate. Then require its parent APPROVED, vendor and currency equal the batch, ledger ID equal the payout line, recognized line type consistent with the ledger/refund-adjustment path, and frozen `payableImpactMinor` exactly equal the payout line's amount snapshot under existing minor-unit conversion. Reuse all existing hold, alert, active-membership, correction-coverage and amount checks. Zero or more than one candidate, absent ledger, scope/type/amount mismatch or inactive settlement fails closed with a structured transition blocker; no auto-selection.
4. Ensure the effective resolved settlement line is unique within this payout and not claimed by a different active payout. A pair of NULL-linked lines must not both borrow the same resolved settlement line. Modern direct lines and historical NULL lines must be considered together for membership/conflict checks; otherwise the nullable FK's relation query can miss legacy claims. This is a validation requirement, not permission to reallocate sources.
5. Resolve from persisted local financial history, not a later Shopify read. Audit F's deterministic 11-row observation supports testing a candidate compatibility route, but fresh read-only prechecks must confirm current status, uniqueness, amounts and blockers before any production transition.
6. New ordinary payout preparation must continue to persist the exact direct settlement-line ID. A NULL on a newly created line is a regression; the compatibility branch must not become a normal writer path. The current schema has no reliable immutable "legacy version" marker, so NULL + proven unique frozen local lineage is a **structural compatibility shape**, not proof of creation date. Do not invent a calendar cutoff. If product insists on historical identity rather than structural eligibility, that requires separate provenance/approval before implementation.
7. A PAID payout must remain terminal, and its backing approved settlement must not become CANCELLED solely because an ordinary historical payout line lacks the newer direct FK. Settlement cancellation must recognize directly linked PAID lines under the existing guard and uniquely proven historical PAID lines under the same authoritative local-lineage semantics used for payout transitions. No historical payout row is backfilled or rewritten.

### REVIEW transition

Within the transition transaction, each line uses either its direct ID or a strictly validated unique historical resolution. The resolver should produce an in-memory effective settlement-line view for the complete current validator, including correction coverage that currently traverses `line.settlementApprovalLine`. A successful DRAFT → REVIEW changes only the authorized payout status; it does **not** populate a formerly NULL direct field or alter settlement/ledger authority. A missing/ambiguous/ineligible match returns a blocker and leaves DRAFT unchanged. A successful match is not a waiver for late refunds, return/cancellation holds, voided/paid ledger, amount drift or another active payout.

### Mark Paid transition

Re-resolve and revalidate in the Mark Paid transaction after its existing batch row lock. Do not rely on a REVIEW-time result: source state can change between transitions. The same effective line IDs used by revalidation must be passed to `buildPayoutPaidEvents`, whose current metadata and idempotency key require the settlement-line ID. They remain stable only when the candidate remains uniquely authoritative; newly missing/ambiguous/inactive lineage fails closed before PAID, ledger update or events. The paid event should reference the proven settlement-line ID, while the historical payout row may remain NULL; no synthetic ID or metadata-only authority. Existing PAID rejection, unique FinanceEvent idempotency and transaction rollback remain. Any uncertainty around event/source consistency under concurrent settlement changes needs isolated PostgreSQL proof before release.

### Settlement cancellation protection

Within the existing settlement cancellation transaction, preserve direct `settlementApprovalLineId` as authoritative for modern payout lines and preserve their current PAID/`paidAt` cancellation guard. For an ordinary historical payout line with NULL direct link and a ledger ID, recognize membership in the settlement being cancelled only after checking **all** local `SettlementApprovalLine` candidates for that ledger, not an APPROVED-only subset. A uniquely proven line must satisfy the same ledger identity, parent settlement, vendor, currency, type and frozen amount/scope authority required by transition compatibility. If its payout is PAID or has `paidAt`, cancellation of that backing settlement must be rejected under the existing PAID terminality rule. A historical unpaid DRAFT must not acquire a PAID-only cancellation block merely because its lineage is derivable; preserve existing status semantics.

Zero candidates do not establish settlement membership; do not invent a link. If more than one candidate exists and the settlement being cancelled is among them, do not select one or dismiss a possible PAID relationship: fail closed for cancellation until the ambiguity is resolved through a separately approved mechanism. A present but invalid/conflicting direct reference must never fall back to ledger derivation. Leave unrelated settlement cancellation behavior and correction-specific guards unchanged. Where safe, use the same authoritative legacy-lineage semantics as REVIEW/Mark Paid; avoid divergent definitions without prescribing a broad shared abstraction. The cancellation check and PAID transition must be serialized/revalidated sufficiently that a race cannot commit PAID against a cancelled backing settlement. Prove this in isolated PostgreSQL before release.

### Historical detection and current payout creation

No repository field establishes a trustworthy pre-/post-migration version for each payout line. `createdAt` alone is not approved as a cutoff, and migration date is not proof of row provenance. The narrow structural fallback is NULL direct link + required ledger ID + exactly one total candidate + valid frozen amount/type/scope + current unpaid transition state. It applies only to ordinary payout lines; correction payout/source rows retain their own lineage. This cannot distinguish a future malformed NULL row from a historical NULL row, so protect the **writer** with a direct-link regression and diagnostics for any newly observed NULL. If an immutable, auditable age/provenance restriction is required, that is missing evidence, not a reason to fabricate a cutoff. Current `preparePayoutBatch` already writes the direct link, so FIN-BUG-009 remains a historical compatibility issue rather than a proven broad writer defect.

## Option assessment

| Option | History / audit and authority risk | REVIEW, PAID, cancellation, new payouts | Concurrency, rollback, migration, approval |
| --- | --- | --- | --- |
| **A. Strict runtime compatibility** — direct link first; NULL-only unique all-status ledger resolution, then normal checks. | Non-destructive. Audit F's mapping can be re-proven at runtime; no silent field change. Must pass effective ID through all validator and PAID event/coverage consumers. | Supports both transitions only if settlement cancellation also recognizes uniquely proven historical PAID membership; modern direct links remain primary. | Re-evaluate on each transition and cancellation; test competing claims/status changes and cancellation-versus-PAID races in real PG. | **B. One-time backfill of historical direct IDs.** | Changes historical payout rows and makes inferred lineage look originally persisted; needs explicit before/after audit and could conceal uncertainty. Audit F matches alone do not authorize it. | Existing REVIEW/PAID and direct-link cancellation checks may then work, but freshness/holds still apply. | **C. Separate immutable compatibility/remediation record.** | Retains original NULL and an auditable mapping decision; introduces a new authority that must be consulted consistently. | Can support both transitions only if validator/event/coverage code reads it; paid-linked settlement cancellation must also consult it. Justified only if audit requirements cannot be met by strict runtime proof. Product/finance approval required. |
| **D. Leave historical DRAFTs blocked and cancel/recreate manually.** | Smallest code delta (none), but cancellation/recreation changes batch identity and potentially frozen payout/debt source set. It is **not** equivalent to preserving the three existing DRAFTs. | No compatibility for REVIEW/PAID; current cancellation remains. New direct-link payouts may prepare from then-current sources only. | No code migration, but material production finance workflow and external EFT uncertainty demand separate decision and authorization; not a safe default. |

**Recommendation: Option A, strict runtime compatibility, as the implementation target only when paid-linked settlement cancellation protection is included.** The isolated PostgreSQL failure disproved the earlier assumption that payout-transition compatibility could safely leave settlement cancellation untouched. The route remains non-destructive if the effective line is used consistently for REVIEW, Mark Paid events/coverage and the existing PAID settlement-cancellation guard, with ambiguity/amount/status/membership checks and race proof. Option B mutates historical rows; C adds authority/schema complexity; D discards the goal of retaining usable DRAFTs. This is not a claim that the three production batches are presently transition-eligible or authorization for a production transition. If the narrow cancellation protection cannot be proven without broadening finance semantics, stop and reassess before release.

## Production boundary, rollout, rollback and closure

**Code compatibility deployment (A):** A later, separately approved release could add the strict local resolver, narrow paid-linked settlement-cancellation protection and tests without a Prisma migration or direct production data mutation. It must remain disabled or fail closed until isolated tests and a fresh read-only production precheck show that the targeted batch/line IDs still have one total lineage candidate each, exact amount/type/vendor/currency/APPROVED status, no conflicting active claim, and no other transition blockers. A successful deployment alone does not move any batch; Admin still explicitly requests REVIEW and later Mark Paid only after the external payment workflow. Modern and unrelated settlement cancellation behavior remains under its existing policy.

**Production data remediation (B/C): NOT AUTHORIZED.** If runtime compatibility proves insufficient, design a separate, auditable procedure with exact targeted records, fresh read-only precheck, approved mutation authority, backup/recovery plan and controlled after-check. Do not write or run backfill SQL now, silently fill the 11 IDs, or alter amounts/history. Do not assume production EFT state from DRAFT.

**Rollback:** Reverting compatibility code returns NULL-linked payouts to their prior blocked state without undoing a completed manual transition. A payout once legitimately marked PAID remains terminal; financial history and external EFT cannot be rolled back by code deployment. Any contemplated DB backfill would need its own separately approved rollback boundary.

**FIN-BUG-009 remains OPEN** until: historical NULL-line fixture and uniqueness proof; REVIEW and Mark Paid compatibility where applicable; missing/ambiguous/ineligible fail-closed cases; modern direct-link behavior unchanged; paid-linked settlement cancellation protection for direct and uniquely resolved historical lines; unpaid, ambiguous and unrelated cancellation behavior preserved; relevant correction/PAID regressions; real PostgreSQL/integration and concurrent cancellation-versus-PAID proof; controlled deployment; post-deploy read-only production verification; and, if needed, separately authorized, controlled production transition verification. An actual production transition result is currently UNKNOWN.
