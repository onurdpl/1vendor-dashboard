# Operational Signal Deduplication Model

## Purpose

The operational workspace currently has many useful signals, but one real issue can fan out into several equal-looking UI artifacts:

```text
raw event -> operational signal -> automation action -> notification -> dashboard card -> queue row -> timeline entry -> linked record
```

This document defines the model that should sit between raw system evidence and user-facing projections before dashboard count normalization is implemented.

This is a discovery and design document only. It does not change backend logic, delete historical records, add schema, normalize dashboard counts, change automation behavior, change finance calculations, or change support workflow semantics.

## Current Source Inventory

| Source concept | Current implementation | Current role | Deduplication already present | Deduplication gap |
| --- | --- | --- | --- | --- |
| Webhook/event evidence | `WebhookEvent`, `OperationalJob`, provider snapshots, return/fulfillment/order records | Raw operational evidence | Webhook idempotency and job IDs are preserved | Not consistently projected into one issue group |
| Operational signal | `OperationalSignal` generated by `evaluateOperationalSignals` | Normalized active condition from rules | Deterministic `signal-${ruleKey}-${subjectId}` IDs | Counts are raw active signals; no grouped issue layer |
| Automation alert | `getAutomationDashboard` derives alert DTOs from allocations, returns, fulfillments, failed webhooks | Automation page alert row | Alert IDs are deterministic per source record | Separate from `OperationalSignal`, so dashboard may count both |
| Automation action | `AutomationAction` generated from operational signals | Operator suggestion/action candidate | Deterministic `automation-${type}-${signalId}` IDs | Actions can become another projection of the same signal |
| Notification | `NotificationIntent` generated from active signals and automation actions | Delivery/history artifact | Notification IDs include channel, role, recipient, signal/action | Read/dismiss lifecycle can be mistaken for issue lifecycle |
| Admin operations queue | `getAdminOperationsQueue` and `getAdminOperationsAttentionCenter` | Admin queue projection | Queue de-dupes by item ID only | Operational signal, automation action, support, shipment, return, and finance entries can describe the same issue separately |
| Support ticket | `SupportTicket` plus notes/replies | Human workflow artifact | Order Detail has local support-ticket dedupe by context/status/subject | Historical duplicate tickets still surface unless grouped by issue context |
| Finance row | `FinanceLedgerEntry`, payout batch, invoice executions | Settlement/reconciliation entity | Finance rows are stable records | Finance issue count is not separated from currency estimates |
| Return/refund row | `ReturnRecord`, `RefundRecord` | Return/refund lifecycle entity | Stable record IDs | Return attention uses different predicates in dashboard and Returns page |
| Timeline item | `OperationalTimeline`, page-local timeline arrays | Contextual history projection | Vendor/admin visibility filters exist | Timeline entries can repeat the same issue already shown as a card/queue/link |
| Linked record | `OperationalLinkCards`, page-local cross-links | Navigation context | Vendor/admin visibility filters exist | Linked records can repeat support/finance/return issue emphasis |

## Definitions

### Raw Event

A low-level occurrence or evidence record. It may be important, but it is not necessarily a user-facing action item by itself.

Examples:

- webhook failed
- fulfillment watcher ran
- allocation remained awaiting shipment
- return request was approved
- Navlungo provider returned a diagnostic response
- finance ledger row was created
- support reply was added

Raw events must remain available for audit and diagnostics. They should not be used directly as dashboard action counts unless the UI says "raw events".

### Signal

A normalized actionable condition derived from raw state.

Examples:

- `shipment_stale`
- `return_aging`
- `shipping_cost_missing`
- `support_unread`
- `finance_review_required`
- `provider_diagnostic_attention`

Signals should be deterministic and idempotent. Current `OperationalSignal` records already follow this pattern for rules-engine signals using deterministic IDs from `ruleKey + subjectId`.

### Operational Issue Group

A deduplicated user-facing issue. This is the missing conceptual layer.

Examples:

- `28 stale fulfillment allocations`
- `3 support tickets for order #1061`
- `1 shipping cost missing issue`
- `4 return requests aging`
- `2 finance rows held for review`

An issue group may contain multiple raw events, signals, tickets, notifications, and timeline entries. The group is what dashboard action counts should usually count.

### Queue Item

A workflow item requiring action in a specific workspace.

Examples:

- one order allocation awaiting shipment
- one return request requiring review
- one open support ticket requiring reply
- one finance row requiring settlement review
- one grouped automation issue requiring admin review

Queue items must link to a workspace where the same item or group is visible.

### Notification

A delivery/history artifact. It tells a user something happened or needs awareness, but it is not the source of truth for whether the issue is active.

Rules:

- Read notification does not resolve the issue.
- Dismissed notification does not resolve the issue.
- Resolved issue can keep notification history.
- Notification counts belong in passive notification history unless explicitly labeled unread notification count.

### Timeline Event

A contextual history projection inside a detail workspace. It describes what happened over time.

Rules:

- Timeline entries are not separate queue items.
- Timeline entries should not compete visually with the primary issue on the same page.
- Admin-only diagnostics may appear in admin timelines, but vendor timelines should remain operational and safe.

### Linked Record

A navigation/context projection that connects related orders, returns, support tickets, finance rows, shipments, and diagnostics.

Rules:

- Linked records preserve evidence and drilldown paths.
- Linked records should be grouped when several records represent the same issue context.
- Linked records should not inflate dashboard action counts.

## Entity Boundaries

| Entity | Owns | Does not own |
| --- | --- | --- |
| Raw event | Evidence and audit trail | User-facing count semantics |
| Signal | Normalized active condition | Delivery lifecycle or support workflow |
| Operational issue group | Deduplicated operational meaning | Raw event storage or provider behavior |
| Queue item | Work execution path | Historical notification status |
| Notification | Delivery/read/dismiss state | Issue resolution state |
| Timeline event | Contextual history | Active workload count |
| Linked record | Navigation and evidence context | Primary issue severity |

## Current Duplication Patterns

### Fulfillment Stale Example

One stale allocation can currently appear as:

- `OperationalSignal` with rule key `fulfillment.stale_awaiting_shipment`
- `NotificationIntent` for the signal
- `AutomationAction` suggestion such as "Review stale fulfillment"
- Admin operations queue item as `operational_signal`
- Dashboard automation signal count
- Dashboard recent operational event
- Orders row with awaiting shipment/tracking missing state
- Order Detail timeline/status card

Desired model:

```text
allocation stale evidence
-> signal: stale_fulfillment on allocation
-> group: stale fulfillment for allocation/order/vendor
-> projections:
   dashboard count: 1 grouped fulfillment issue
   queue row: one allocation work item
   notification: passive history/unread notice
   timeline: context only
   linked records: order/support/finance navigation only
```

### Support Duplicate Example

Historical support duplicates can currently appear as:

- multiple `SupportTicket` rows
- Support page rows
- Finance linked records
- Order Detail linked records
- Order/Return timeline items
- dashboard notification count if related notifications exist

Desired model:

```text
3 support tickets for order #1061
-> group: support activity for order #1061
-> dashboard support count: one grouped support issue or three open tickets, depending label
-> linked records: one support activity card with expandable ticket history
-> timeline: latest support event plus expandable history, not three equal primary events
```

### Finance Review Example

One finance row can currently appear as:

- `FinanceLedgerEntry`
- Finance table row
- Finance inspector settlement preview
- Order Detail settlement preview
- Order Detail finance timeline
- Admin operations finance attention row
- possible operational signal or notification

Desired model:

```text
finance row held/disputed/failed invoice
-> signal: finance_review_required
-> group: finance review for row/order/vendor
-> dashboard count: one finance review item
-> finance table: one row
-> order detail: settlement context only
-> notification: passive history
```

## Deduplication Keys

### General Key Shape

Use a stable, explicit grouping key:

```text
vendorId + issueType + primaryEntityType + primaryEntityId
```

Optional modifiers can be added only when they truly create separate user work:

```text
severityClass + workflowOwner + provider + lifecyclePhase
```

Avoid keys based only on title text. Title-based grouping is useful for UI fallback, but it is not stable enough for operational truth.

### Fulfillment

Primary key:

```text
vendorId + issueType + allocationId
```

Fallback key:

```text
vendorId + issueType + orderId
```

Recommended issue types:

- `shipment_stale`
- `tracking_missing`
- `shipment_provider_failed`
- `allocation_blocked`
- `reassignment_required`

Notes:

- If one order has multiple vendor allocations, allocation-level keys are safer than order-level keys.
- Order-level grouping can be a display grouping above allocation-level queue items.

### Returns

Primary key:

```text
vendorId + issueType + returnRequestId
```

Fallback keys:

```text
vendorId + issueType + shopifyReturnId
vendorId + issueType + returnRecordId
vendorId + issueType + orderId
```

Recommended issue types:

- `return_review_required`
- `return_aging`
- `return_pickup_blocked`
- `return_provider_failed`
- `refund_impact_pending`

Notes:

- Shopify return request IDs are preferable when present.
- Order-level grouping is useful for display, but individual return requests remain distinct workflow items.

### Finance

Primary key:

```text
vendorId + issueType + financeRowId
```

Fallback key:

```text
vendorId + issueType + orderId
```

Recommended issue types:

- `finance_review_required`
- `shipping_cost_missing`
- `invoice_visibility_failed`
- `settlement_held`
- `payout_review_stale`
- `negative_vendor_payable`

Notes:

- Finance row IDs should drive review item counts.
- Currency amounts remain values on the group, not the group count.

### Support

Primary key:

```text
vendorId + linkedEntityType + linkedEntityId + category
```

Fallback key:

```text
vendorId + category + normalizedSubject
```

Recommended issue types:

- `support_open`
- `support_unread`
- `support_waiting_for_vendor`
- `support_overdue`
- `support_escalated`

Notes:

- Ticket records remain canonical support workflow records.
- Grouping should not delete or mutate duplicate historical tickets.
- A support issue can be resolved when the relevant ticket set has no open/actionable tickets, but this does not resolve the shipment/return/finance issue that caused the ticket.

### Automation

Primary key:

```text
vendorId + ruleType + affectedEntityId
```

Fallback key:

```text
vendorId + ruleKey + sourceArea + affectedEntityId
```

Recommended affected entity priority:

1. allocationId
2. returnRecordId or shopifyReturnId
3. financeLedgerEntryId
4. payoutBatchId
5. operationalJobId
6. vendorId

Notes:

- Current `OperationalSignal` deterministic ID already approximates this for rule signals.
- Dashboard automation count should use grouped active issue count, with raw signal count available as admin drilldown.

### Notifications

Notification grouping key:

```text
recipientRole + vendorId + signalType + linkedEntityId + severity
```

Fallback key:

```text
recipientRole + vendorId + normalizedTitle + sourceArea + severity
```

Notes:

- Notification grouping is presentation only.
- Notification grouping does not define issue identity.
- Dismissed notification should not remove the issue group from active queues.

## Dashboard Count Semantics

Dashboard cards and queues should count operational issue groups unless they are explicitly labeled as raw records or history.

| Dashboard surface | Count should represent | Should not represent |
| --- | --- | --- |
| Needs attention | Sum of active issue groups that need action in the selected scope | Raw signals + notifications + currency values mixed together |
| Fulfillment queue | Active fulfillment/shipment issue groups or allocation work items | Every timeline event or notification related to shipment |
| Returns queue | Return/refund issue groups requiring review | Processed return history |
| Support queue | Open support ticket groups or unread support replies, depending label | General unread notifications |
| Automation queue | Active grouped automation/rules issues | Raw rule signal count unless labeled raw |
| Finance review queue | Finance rows/groups requiring review | Settlement estimate currency |
| Notification history | Raw or grouped notifications, explicitly passive | Active workload count |
| Workspace status | Low-priority narrative summary | Primary count source |

Recommended explicit labels:

- `Open support issues`
- `Unread support replies`
- `Active automation issue groups`
- `Raw rule signals`
- `Finance rows needing review`
- `Settlement estimate`
- `Unread notifications`

## UI Projection Rules

### One Issue, Many Projections

One operational issue group may appear in multiple places, but each projection must have a distinct purpose.

| Projection | Purpose | Visual weight |
| --- | --- | --- |
| Dashboard card | Summary/action count | Primary on dashboard only |
| Queue row | Work execution | Primary in the destination queue |
| Notification history | Delivery/audit | Passive |
| Timeline entry | Contextual history | Secondary on detail pages |
| Linked record | Navigation context | Secondary |
| Diagnostics | Investigation detail | Admin-only or collapsed |

### Same Page Rule

Do not render the same issue group as multiple equal-priority items on the same page.

Examples:

- If support activity is already the primary linked record group, support timeline entries should be secondary or expandable.
- If a finance row is selected in Finance inspector, related support tickets should be grouped as support activity, not repeated as separate headline cards.
- If a return pickup provider error is the primary Operations issue, raw request/response diagnostics should be collapsed below it.

### Priority Rule

Actionable projections outrank passive projections:

1. Primary action or queue item
2. Current lifecycle status
3. Linked records
4. Timeline history
5. Notification history
6. Raw diagnostics

### Evidence Preservation Rule

Deduplication is presentation and counting only. It must not:

- delete support tickets
- delete notifications
- mutate raw signals
- hide admin diagnostic evidence
- collapse provider snapshots beyond visibility controls
- weaken auditability

## Lifecycle Model

### Raw Event Lifecycle

Raw events are immutable or append-only evidence. They may be replayed, reprocessed, or marked with processing status, but they should not be treated as active dashboard workload by themselves.

### Signal Lifecycle

Current `OperationalSignal` supports:

- `active`
- `acknowledged`
- `resolved`
- `ignored`

This is useful for rule output. It should not be conflated with notification read/dismiss or support ticket status.

### Proposed Operational Issue Group Lifecycle

Future issue groups should use:

- `active`: issue exists and needs attention.
- `acknowledged`: operator saw it; issue still exists.
- `in_review`: issue has an owner or linked workflow in progress.
- `resolved`: underlying condition no longer needs action.
- `dismissed`: hidden from a specific UI projection without resolving underlying condition.
- `historical`: retained for timeline/history only.

Transition rules:

- Dismissed notification does not resolve issue group.
- Read notification does not acknowledge issue unless explicitly mapped.
- Support ticket close may resolve a support issue group but not a shipment/return/finance issue group.
- Operational signal resolution can resolve an automation/rules issue group when no other active evidence remains.
- Provider success can resolve a provider failure issue group, while keeping prior failure evidence in history.
- Finance row status change can resolve finance review issue group if no held/disputed/failed condition remains.

## Vendor/Admin Visibility

### Vendor

Vendor users should see grouped actionable issues and limited passive history.

Vendor-safe examples:

- `3 orders awaiting shipment`
- `1 return needs review`
- `2 unread support replies`
- `1 settlement estimate awaiting review`
- `Shipping cost pending` only when expressed as vendor-safe settlement preview language

Vendor users should not see:

- raw diagnostics/reconciliation spam
- global admin notifications
- internal operational job details
- raw provider request/response dumps by default
- duplicate support/history items as separate high-priority tasks

### Admin

Admin users can see grouped issues plus drilldown into raw evidence.

Admin-safe examples:

- grouped automation issue count plus raw signal count
- support issue group plus duplicate ticket history
- finance review row plus invoice/provider diagnostics
- operational job issue plus raw job/retry metadata
- notification history grouped by signal/action

Admin surfaces should label raw evidence clearly:

- `Raw signals`
- `Notification history`
- `Provider diagnostics`
- `Operational job evidence`
- `Support ticket history`

## Proposed Data Shape, No Schema Yet

The frontend/backend DTO can model issue groups before schema is added:

```ts
type OperationalIssueGroup = {
  id: string;
  issueType: string;
  status: 'active' | 'acknowledged' | 'in_review' | 'resolved' | 'dismissed' | 'historical';
  severity: 'info' | 'warning' | 'high' | 'critical';
  vendorId: string | null;
  primaryEntityType: 'allocation' | 'order' | 'return' | 'finance_row' | 'support_thread' | 'automation_signal' | 'operational_job';
  primaryEntityId: string;
  title: string;
  summary: string;
  count: number;
  rawSignalCount?: number;
  notificationCount?: number;
  supportTicketCount?: number;
  latestActivityAt: string;
  oldestActivityAt?: string;
  destinationPath?: string;
  visibility: 'vendor' | 'admin' | 'shared';
  evidenceRefs: Array<{
    type: 'signal' | 'notification' | 'support_ticket' | 'finance_row' | 'return' | 'order' | 'job' | 'timeline_event';
    id: string;
  }>;
};
```

This type should remain DTO-only in Phase A/B.

## Source-to-Projection Rules

| Source | Can create signal | Can create issue group | Can create queue item | Can create notification | Can create timeline item |
| --- | --- | --- | --- | --- | --- |
| Webhook event | Sometimes | Only through normalized state | Rarely | No direct dashboard notification unless normalized | Yes, as detail history |
| Operational job | Yes, for escalated/failure states | Yes | Admin only | Admin only | Yes |
| Operational signal | Already normalized | Yes | Yes | Yes | Yes, secondary |
| Automation action | No, derived from signal | Usually no separate group | Yes, admin action queue | Yes, history | Yes, if executed/failed |
| Support ticket | Yes, if support workflow requires action | Yes | Yes | Maybe, if reply/unread | Yes |
| Finance ledger row | Yes, if held/disputed/failed/missing input | Yes | Yes | Maybe | Yes |
| Return record | Yes, if requested/aging/provider blocked | Yes | Yes | Maybe | Yes |
| Notification | No | No | No | Itself | No, unless explicitly shown as history |

## Implementation Phases

### Phase A: Frontend Grouping and Projection Only

Use existing dashboard, support, automation, finance, return, and notification data. No schema changes.

Actions:

- Create shared frontend grouping helpers for issue-like data.
- Stop using notification unread count as support queue count unless label says unread notifications.
- Count grouped automation issues separately from raw signals.
- Group support history by linked context on Dashboard, Finance, Order Detail, and Return Detail.
- Keep raw record counts visible only in secondary/admin labels.
- Add tests that prove grouped counts do not equal raw notification/signal counts accidentally.

Expected result:

- Dashboard becomes semantically honest without backend contract changes.
- Historical evidence remains accessible.

### Phase B: Backend DTO Normalization

Add a backend or shared aggregate endpoint that returns normalized issue groups while still reading existing records.

Actions:

- Build dashboard DTOs around `OperationalIssueGroup` semantics.
- Include both group counts and raw evidence counts.
- Add destination filter hints for each group/card.
- Keep existing `/signals`, `/notifications`, `/automation`, `/support`, `/finance`, `/returns`, and `/orders` behavior unchanged.

Expected result:

- Dashboard counts are owned by one contract.
- Destination pages can consume the same grouping logic if needed.

### Phase C: Persist `OperationalIssueGroup`

Only after DTO semantics are proven, add schema if necessary.

Candidate fields:

- id
- issueType
- status
- severity
- vendorId
- primaryEntityType
- primaryEntityId
- title
- summary
- firstSeenAt
- lastSeenAt
- resolvedAt
- dismissedAt
- metadata

Candidate relationships:

- OperationalSignal
- NotificationIntent
- AutomationAction
- SupportTicket
- FinanceLedgerEntry
- ReturnRecord
- VendorAllocation
- OperationalJob

Expected result:

- Stable group lifecycle independent of individual projections.
- Cleaner audit and admin drilldown.

### Phase D: Admin Raw Evidence Drilldown

Expose raw evidence only where it helps admin investigation.

Actions:

- Show group summary first.
- Add expandable raw signals, notifications, jobs, provider diagnostics, support history, and finance rows.
- Preserve vendor-safe grouping.
- Add audit notes showing why records are grouped.

Expected result:

- Admin can investigate without making vendor dashboards noisy.

## Migration and Backfill Notes

No historical records should be deleted or rewritten.

Recommended migration behavior if persisted groups are added later:

- derive groups from existing active records.
- preserve historical support duplicate records.
- attach evidence references without mutating source records where possible.
- use deterministic group IDs so reruns are idempotent.
- mark groups historical only when no active evidence remains.

## Testing Strategy

Phase A tests:

- dashboard support count does not use generic notification unread when labeled support queue.
- automation group count differs from raw signal count when multiple signals share a group.
- finance queue count is numeric review rows, while settlement estimate remains currency.
- support duplicate tickets are grouped visually with history access.
- notification dismissal does not remove active issue group.

Phase B tests:

- backend aggregate returns group count and raw evidence count separately.
- vendor aggregate excludes admin-only diagnostic groups.
- admin aggregate includes raw evidence metadata without secrets or full payloads.
- destination filter hints match visible destination pages.

Phase C tests:

- deterministic group ID upsert is idempotent.
- issue lifecycle survives notification read/dismiss.
- issue resolves only when underlying evidence is resolved.
- historical evidence remains linked after resolution.

## Non-Goals

- Do not delete duplicate support tickets.
- Do not mutate notification history.
- Do not change Shopify, provider, finance, return, fulfillment, or support business logic.
- Do not weaken webhook idempotency or HMAC verification.
- Do not make notifications the source of active issue truth.
- Do not treat currency values as queue counts.
- Do not expose vendor-unsafe diagnostics.

## Unresolved Decisions

- Should dashboard support primary count mean open support issue groups or unread support replies?
- Should automation issue groups include vendor-safe rule signals for vendors, or only admin-owned automation?
- Should fulfillment dashboard counts group by allocation or by order when one Shopify order has multiple vendor allocations?
- Should return queue count Shopify return requests only, or include refund webhook records requiring reconciliation?
- Should finance review count held/disputed rows, failed invoice rows, blocked payout rows, or all of them as separate issue types?
- Should acknowledged issue groups stay visible on vendor dashboards or move to secondary history?
- Should notification dismissal be user-specific only, or can it dismiss one projection for a role/scope?

## Recommended Next Step

Implement Phase A only:

1. Add frontend grouping helpers for operational issue groups.
2. Normalize dashboard card semantics without schema changes.
3. Keep raw signals, notifications, support tickets, and finance rows accessible as evidence.
4. Add regression tests proving dashboard counts match destination-page semantics or are explicitly labeled as raw/history.
