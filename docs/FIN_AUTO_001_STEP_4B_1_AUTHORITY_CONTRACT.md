# FIN-AUTO-001 — Step 4B.1 automatic settlement approval authority contract

**Status:** Design/evidence contract only (2026-10-14). Step 4A is CLOSED; Step 4B write worker is NOT STARTED. The classifications below are documentation labels, not application statuses or approval permission.

## Objective and evidence key

**Approved objective:** verifiable normal finance operations should advance from DRAFT through APPROVED, Logo invoice, payout DRAFT and pre-payment validation without routine Admin approval. Unresolved evidence goes to Finance Review. External EFT and Mark Paid remain manual. This contract does not restrict refund, correction or replacement transactions to permanent manual handling; it also does not authorize any subtype for unattended writes.

Evidence labels used below: **VERIFIED_IN_CODE** means current source behavior; **SUPPORTED_BY_TEST** means an existing named test exercises it; **TECHNICAL_RECOMMENDATION** is an implementation proposal, not a rule; **REQUIRES_USER_APPROVAL** is an unresolved financial/authorization choice; **UNKNOWN** means not established. Historical design prose in [FINANCE_SETTLEMENT_MODEL.md](FINANCE_SETTLEMENT_MODEL.md) and [FINANCE_LEDGER_MODEL.md](FINANCE_LEDGER_MODEL.md) is not a substitute for current write-path evidence. No Shopify behavior is inferred from a webhook envelope; accepted monetary-refund authority follows [REFUND_ADJUSTMENT_LIFECYCLE.md](REFUND_ADJUSTMENT_LIFECYCLE.md#policy) and [SHOPIFY_DISCOVERIES.md](SHOPIFY_DISCOVERIES.md).

## Current architecture and canonical authority

**VERIFIED_IN_CODE:** Step 4A first scopes the approval by `id` and `vendorId`, then calls canonical `assessSettlementApprovalReadiness`. It returns `BLOCKED` for non-DRAFT or failed current-source validation, `UNKNOWN` for unverified readiness, replacement/correction authority, missing ordinary lines or refund-bearing subtype policy, and `ELIGIBLE_EVIDENCE_ONLY` only for an ordinary SALE DRAFT with verified existing checks. Every result has `writesPerformed: false`, `approvalAuthorized: false`, `requiresWriteTimeRevalidation: true`. The profile's active/auto-approve flags are reported, **not** a write authorization gate (`C`; `T:139-228`). Readiness uses a separate RepeatableRead read transaction (`A:1438-1504`); its result can be stale.

**VERIFIED_IN_CODE:** The actual Admin route authenticates and requires `role === 'admin'`, then passes `request.authUser.id` to `approveSettlementApproval` (`backend/src/modules/finance/finance.routes.ts:2205-2230`). The exported service itself takes an ID and nullable actor string; it does not authenticate the caller (`A:2732-2735`). It reads the current DRAFT inside a Serializable transaction. Ordinary lines are reloaded and checked for exact vendor/type, active ledger and payout status, another active settlement/payout claim, current refund count, return/cancellation/vendor-blocked holds, frozen delay and line amounts. Adjustment lines verify exact application/adjustment identity, vendor, ledger, state and amount. Blocking integrity alerts are checked for each loaded row (`A:888-1399`; `T:2286-2699`). This is canonical validation, not a new engine.

**VERIFIED_IN_CODE:** The same transaction additionally checks controlled-replacement original/cutoff/source and late-refund bridge identity; reconciles correction credit/deduction totals and calls their active-authority checks; updates only the approval to `APPROVED` with `approvedBy` and `approvedAt`; and, for verified replacement bridges, creates pending refund adjustments. Failure throws and rolls back the transaction (`A:2732-2869`; `R`). Ordinary approval does not itself create an invoice or payout. For replacement the vendor row is locked before revalidation; no equivalent explicit vendor row lock is visible for ordinary approval (`A:2738-2743`). Serializable isolation is present, but two-worker/Admin races still need PostgreSQL proof.

## Vendor, actor and write-time authorization boundary

**VERIFIED_IN_CODE:** `VendorFinancialProfile.active` defaults true and `autoSettlementApproveEnabled` defaults false (`P:571-591`). Profile editing persists and audits that flag (`backend/src/modules/finance/finance.service.ts:4880-4930`; `backend/src/modules/vendors/vendor-profile-audit-log.service.ts:63`). The schedule service warns when auto-approve is configured but does not approve (`backend/src/modules/finance/settlement-schedule.service.ts:269-284`). A repository search found no production caller that uses the flag to authorize `approveSettlementApproval`; the only current HTTP call is Admin-authenticated (`finance.routes.ts:2205-2230`). **UNKNOWN:** what opt-in policy should apply to manually created DRAFTs and mid-flight profile changes.

**VERIFIED_IN_CODE:** `SettlementApproval.approvedBy` is nullable `String?`, with no `User` relation; `approvedAt` is nullable `DateTime?` (`P:1955-1958`). Other services use `system:` attribution, e.g. `system:settlement_auto_draft_scheduler` and `system:settlement_replacement_approval`, but none is an approved automatic-settlement-approval actor (`settlement-auto-draft-write-scheduler.service.ts:74`; `A:2855`). **TECHNICAL_RECOMMENDATION:** use a stable, explicitly authorized system actor convention and retain an attempt/result correlation; do not impersonate an Admin or pass null. **REQUIRES_USER_APPROVAL:** choose the actor identity/audit contract and whether existing `approvedBy`/`approvedAt` plus operational run evidence suffice or a durable additional audit record is required.

**TECHNICAL_RECOMMENDATION:** expose a narrow internal system-only approval entry point; never publish the bare exported service as a worker authorization API. Under the same Serializable transaction that performs canonical revalidation, require current DRAFT, exact vendor, approved subtype policy, current active/opted-in profile, stable actor, and any source-origin/cutoff rules. The current `approveSettlementApproval` transaction is the financial engine to reuse, not a result to trust from a prior candidate read. Keep the Admin route and its behavior unchanged. An ordinary-approval lock/version strategy and its interaction with Admin approval must be proven, not inferred from Serializable isolation alone. Any change to the canonical transaction or lock order is a later implementation gate, not made here.

## Worker and Finance Review contract

**VERIFIED_IN_CODE:** Existing auto-DRAFT writer is separately gated, explicitly UTC-scheduled, process-overlap guarded and passes a system trigger to its job (`backend/src/modules/finance/settlement-auto-draft-write-scheduler.service.ts:43-115`). It is **not** an approval worker. JobRun uniqueness and cycle claims belong to DRAFT creation, not approval replay (`backend/prisma/schema.prisma:1960-1970,1995-2009`). **TECHNICAL_RECOMMENDATION:** a future approval worker needs its own default-disabled kill switch and explicit cadence; vendor-scoped bounded DRAFT discovery; persistent or reconstructible attempt/outcome evidence; status/actor reconciliation after ambiguous commit; no blind retry of UNKNOWN/FAILED; one-winner PostgreSQL proof for two workers and Admin; and an untouched manual fallback. Do not reuse the DRAFT JobRun as approval authority or select a retry interval here. **UNKNOWN:** whether current tables suffice for durable crash-recovery/attempt reporting; no new table is proposed without evidence.

**VERIFIED_IN_CODE:** Admin list is vendor-scoped but returns the newest 20 approvals (`A:3156-3180`). The selected-DRAFT readiness endpoint is Admin-only and returns canonical blockers or 503 on evaluation failure (`backend/src/modules/finance/finance.routes.ts:1305-1355`). UI queue badges are summary-based, explicitly not verified financial readiness (`src/pages/AdminSettlementApprovalsPage.tsx:1464-1576`). FinanceIntegrityAlert blocks relevant line approval (`A:1388-1399`). **TECHNICAL_RECOMMENDATION:** reuse this review surface and structured blockers, but establish durable exception visibility and bounded discovery before unattended operation. An older unresolved DRAFT may fall outside the latest-20 list. [FIN-UI-016](FINANCIAL_BUGS.md#fin-ui-016--canonical-settlement-readiness-queue--deferred-enhancement-evaluation) remains **OPEN / deferred**; its Option 2 is not approved or automatically required by this contract. Decide whether existing selected-row readiness plus a separate bounded exception listing suffices.

## PostgreSQL acceptance contract for later write packages

**TECHNICAL_RECOMMENDATION:** reuse the existing isolated suites instead of duplicating their fixtures: Step 4A's eight cases (`T`); manual line/revalidation cases (`src/settlement-approval.test.ts:2245-2707`); controlled replacement races (`R`); correction-credit/deduction approved-settlement suites. Add focused disposable-PostgreSQL tests for: clean canonical system approval with actor/time/source/amount unchanged; active/opted-in vendor and flag flipped between candidate and write; missing/inactive profile; post-candidate accepted refund, return/cancellation hold, alert, missing ledger, source/amount change; exact refund/adjustment/correction/replacement authority for each approved subtype; negative/zero-net disposition; Admin-versus-worker and two-worker contention; replay and crash before/after commit; no duplicate adjustment/correction effect; no cross-vendor read/write; immutable APPROVED and PAID history. Assert persisted state, rollback and no invoice/payout/EFT side effects. No production DB execution is authorized by this document.
