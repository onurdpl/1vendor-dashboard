# FIN-AUTO-001 — Step 4B.1 automatic settlement approval authority contract

**Status:** Step 4B.1 design/evidence contract (2026-10-14). Step 4A is CLOSED. A locally callable Step 4B.3 worker and default-disabled scheduler are implemented as noted below; production activation is neither authorized nor verified here. The classifications below are documentation labels, not application statuses or approval permission.

## Objective and evidence key

**Approved objective:** verifiable normal finance operations should advance from DRAFT through APPROVED, Logo invoice, payout DRAFT and pre-payment validation without routine Admin approval. Unresolved evidence goes to Finance Review. External EFT and Mark Paid remain manual. This contract does not restrict refund, correction or replacement transactions to permanent manual handling; it also does not authorize any subtype for unattended writes.

**Subsequent approved decisions (2026-10-17):** automatic settlement approval is a SPORGYM internal finance operation. Vendor opt-in, consent or an approval preference is **not required** and must not be introduced as a write-time prerequisite. The existing `autoSettlementApproveEnabled` field is not automatic approval authority. `AUTONOMOUS_SCHEDULER`, `ADMIN_SCHEDULED`, `ADMIN_MANUAL` and canonically created `CONTROLLED_REPLACEMENT` DRAFT origins are included; Admin creation does not require subsequent manual Admin approval. A legacy `creationOrigin = null` has no automatic authority and is not backfilled. The controlled replacement writer now persists its explicit origin atomically with the predecessor/request/Admin audit and frozen financial snapshot. A PostgreSQL CHECK requires replacement lineage for that origin, and the existing `creationOrigin` UPDATE trigger makes the origin immutable. System approval additionally verifies the replacement audit shape and original scheduled cancellation lineage inside the canonical Serializable transaction, before the existing frozen-source and C11 late-refund checks. Canonical financial eligibility and write-time validation remain mandatory for supported compositions; Step 4A candidate evidence alone is not write permission. If a finance profile becomes inactive after an eligible DRAFT was created, inactivity alone does not block its canonical SYSTEM approval; this does not change new scheduled-DRAFT creation rules. Admin alone owns review of unresolved attempts, errors and financial conflicts; no separate reviewer role or vendor approval is required. The worker and default-disabled five-minute polling scheduler are implemented locally; production activation is not authorized or verified by this document. Logo, payout, EFT and Mark Paid automation are not authorized by this package; EFT and Admin Mark Paid remain manual.

Evidence labels used below: **VERIFIED_IN_CODE** means current source behavior; **SUPPORTED_BY_TEST** means an existing named test exercises it; **TECHNICAL_RECOMMENDATION** is an implementation proposal, not a rule; **REQUIRES_USER_APPROVAL** is an unresolved financial/authorization choice; **UNKNOWN** means not established. ## Current architecture and canonical authority

**VERIFIED_IN_CODE:** Step 4A first scopes the approval by `id` and `vendorId`, then calls canonical `assessSettlementApprovalReadiness`. It returns `BLOCKED` for non-DRAFT or failed current-source validation, `UNKNOWN` for unverified readiness, replacement/correction authority, missing ordinary lines or refund-bearing subtype policy, and `ELIGIBLE_EVIDENCE_ONLY` only for an ordinary SALE DRAFT with verified existing checks. Every result has `writesPerformed: false`, `approvalAuthorized: false`, `requiresWriteTimeRevalidation: true`. The profile's active/auto-approve flags are reported, **not** a write authorization gate (`C`; `T:139-228`). Readiness uses a separate RepeatableRead read transaction (`A:1438-1504`); its result can be stale.

**VERIFIED_IN_CODE:** The actual Admin route authenticates and requires `role === 'admin'`, then passes `request.authUser.id` to `approveSettlementApproval` (`backend/src/modules/finance/finance.routes.ts:2205-2230`). The exported service itself takes an ID and nullable actor string; it does not authenticate the caller (`A:2732-2735`). It reads the current DRAFT inside a Serializable transaction. Ordinary lines are reloaded and checked for exact vendor/type, active ledger and payout status, another active settlement/payout claim, current refund count, return/cancellation/vendor-blocked holds, frozen delay and line amounts. Adjustment lines verify exact application/adjustment identity, vendor, ledger, state and amount. Blocking integrity alerts are checked for each loaded row (`A:888-1399`; `T:2286-2699`). This is canonical validation, not a new engine.

**VERIFIED_IN_CODE:** The same transaction additionally checks controlled-replacement original/cutoff/source and late-refund bridge identity; reconciles correction credit/deduction totals and calls their active-authority checks; updates only the approval to `APPROVED` with `approvedBy` and `approvedAt`; and, for verified replacement bridges, creates pending refund adjustments. Failure throws and rolls back the transaction (`A:2732-2869`; `R`). Ordinary approval does not itself create an invoice or payout. For replacement the vendor row is locked before revalidation; no equivalent explicit vendor row lock is visible for ordinary approval (`A:2738-2743`). Serializable isolation is present, but two-worker/Admin races still need PostgreSQL proof.

**VERIFIED IN LOCAL SOURCE:** `SettlementApproval.approvedBy` and `approvedAt` retain the actor and time; SYSTEM approval uses the fixed `system:settlement_auto_approval` actor, an exact successful-attempt link and immutable attempt events (`backend/src/modules/finance/settlement-approval.service.ts:2782-2796,2968-3006`; `backend/src/modules/finance/settlement-auto-approval.service.ts:7-16`; `backend/prisma/schema.prisma:1972-1974,2015-2044`). ## Worker and Finance Review contract

**Step 4B.3 local worker (not activated):** `runAutomaticSettlementApprovalWorker({ vendorId })` reads that vendor's current DRAFT settlements in creation order. It considers only the four approved non-null creation origins, then invokes `approveSettlementDraftInternally` with an exact vendor and attempt identity. It never uses Step 4A's `ELIGIBLE_EVIDENCE_ONLY` as write permission and performs no monetary calculation. A prior durable attempt is reconciled rather than financially retried; results retain the canonical reconciliation classifications and reason codes. Only an exact previously persisted `vendor_blocked_finance_hold_active` whose authoritative hold has resolved may obtain a new recovery attempt; other BLOCKED reasons are not automatically retried. No batch-size or automatic financial retry policy is configured. Canonical write-time checks remain the sole approval authority; an inactive profile after DRAFT creation does not block SYSTEM approval.

**Step 4B.3 subsequent local scheduler (disabled by default):** `SETTLEMENT_AUTO_APPROVAL_SCHEDULER_ENABLED=false` installs no timer. When explicitly enabled, a separate in-process timer polls every five minutes, with no immediate startup run or event trigger. Each tick reconciles durable STARTED/UNKNOWN attempts first, including attempts whose settlement is already APPROVED, then discovers DRAFT vendors from settlement records rather than financial-profile opt-in or the Admin last-20 list, and invokes the existing vendor-scoped worker. In-process overlap is skipped; shutdown clears the timer. Per-settlement attempt authority and canonical write-time validation remain the cross-instance duplicate protections; no distributed lease, new JobRun, automatic finance retry, payout, invoice, EFT or Mark Paid is introduced. The source default is disabled; actual production flag value is not verified here. Admin is the sole operational owner of unresolved attempts and errors. The authenticated Admin history API/UI shows persisted STARTED, UNKNOWN and BLOCKED attempts and their events. The later local Phase 4.4A separately exposes classified operational failures; it is not an automatic notification and cannot persist during a complete database outage. Real driver commit-ack-loss and isolated database-connection failure remain untested.

**VERIFIED IN LOCAL SOURCE:** The separately gated auto-DRAFT writer is not the approval worker; its JobRun cycle claims are not approval replay authority. The approval worker has a separate default-disabled five-minute scheduler, vendor-scoped DRAFT discovery, durable attempt/outcome evidence, reconciliation before new work and no blind STARTED/UNKNOWN retry (`backend/src/modules/finance/settlement-auto-approval-scheduler.service.ts:25-138`; `backend/src/modules/finance/settlement-auto-approval-worker.service.ts:77-145`). Local PostgreSQL tests cover selected two-process and Admin contention and F-06 process crashes. Real isolated DB-connection loss and Prisma driver commit-ACK loss remain NOT TESTED; local tests are not production activation evidence.

**VERIFIED_IN_CODE:** The settlement list is vendor-scoped but returns the newest 20 approvals. Selected-DRAFT readiness remains Admin-only; queue badges are summary-based, not verified financial readiness. A separate authenticated Admin-only attempt-history API/UI is keyset-paginated and filterable by vendor and outcome, including STARTED, UNKNOWN and BLOCKED (`backend/src/modules/finance/finance.routes.ts:1327-1371`; `backend/src/modules/finance/settlement-auto-approval-review.service.ts:37-93`; `src/pages/SettlementAutoApprovalHistory.tsx:18-135`). FinanceIntegrityAlert blocks relevant line approval (`A:1388-1399`). This persisted history improves Admin visibility but is not an automatic notification or a complete scheduler-error queue. [FIN-UI-016](FINANCIAL_BUGS.md#fin-ui-016--canonical-settlement-readiness-queue--deferred-enhancement-evaluation) remains **OPEN / deferred**; its separate queue enhancement is not assumed necessary here.

**Phase 4.4A local extension (not released):** A separate additive `SettlementAutoApprovalOperationalError` record captures classified scheduler/worker failures that occur without a durable financial attempt. It never represents an APPROVED settlement or authorizes a retry. The recording identity comprises phase, category, safe error code and exact known vendor/settlement/attempt scope; a database uniqueness constraint and atomic upsert retain first/last observed times and increment occurrence count. Raw exception messages and stacks are not stored. A bounded Admin-only read route and a separate operational-errors section on the attempt-history page expose this evidence without changing canonical approval authority. This is best-effort while PostgreSQL is available: a complete database outage cannot persist an error in that same database, and a generic unclassified exception is grouped by its operational class rather than its private text. No automatic resolution, deletion, notification or production activation is implemented. Local disposable PostgreSQL 16 and 18 each passed readiness/operational evidence **54/54**, F-03/F-04 **7/7**, and F-06 **3/3**; focused scheduler/worker/Admin API/UI tests passed **85/85**. Both canonical bootstrap checks passed through migration `20261017130000_add_settlement_auto_approval_operational_error`. These are local results, not remote CI or deployment evidence.
